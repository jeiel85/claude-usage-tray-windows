# 결정 기록

되돌리기 어려운 결정(보안·데이터 형식·공개 API·인프라·주요 의존성)과 그 이유를 남긴다.

## D-1. 자동 업데이트는 배포 PC 의 오프라인 키로 서명한다 (2026-11-18, #290, v1.67.3)

**문제.** PC 앱은 GitHub Release 의 `ClaudeUsageTray.exe` 를 같은 릴리스의 `SHA256.txt` 로만 확인하고 카운트다운 뒤 자동 설치했다. 해시가 exe 와 같은 곳에 있으니 전송 중 손상만 막을 뿐 출처는 증명하지 못한다. GitHub 계정·토큰·워크플로의 Action 중 하나만 탈취돼도 모든 사용자 PC 에서 코드를 실행할 수 있었다 — 보안 감사에서 PC 를 장악할 수 있는 유일한 현실적 경로였다.

**선택지.**

| | 막는 것 | 비용 |
|---|---|---|
| A. 배포 PC 의 오프라인 키 (채택) | GitHub 계정이 탈취돼도 막는다 | 무료. 릴리스마다 배포 PC 에서 서명 한 단계, 키 백업 |
| B. GitHub Actions 보호 환경의 키 | 자산 바꿔치기·Action 탈취 | 무료·완전 자동. 계정 탈취는 못 막는다 |
| C. Authenticode 코드 서명 | A 와 비슷 + SmartScreen | 월 요금·신원 확인, 개인 가용성 불확실 |
| 현행 유지 | 전송 손상만 | — |

**결정.** A. 릴리스는 원래 이 PC 에서 에이전트가 진행하므로 서명 단계를 붙이기 쉽고, 막는 범위가 가장 넓다.

**방식.**
- 키: ECDSA P-256(.NET 기본 제공, 추가 의존성 없음). 개인키는 메인 체크아웃 `.keystore/update-signing.pem`(PKCS#8, AES-256·PBKDF2 60만 회로 암호화) + 비밀번호 `.keystore/update-signing.properties`, 둘 다 git 제외. 백업은 `G:\내 드라이브\모바일 앱 개발\Claude Usage Tray\릴리즈 키스토어\`. 공개키는 `UpdateSignature.PublicKeyPem` 에 내장.
- 서명 내용: `"claude-usage-tray-update/v1\n<버전 x.y.z>\n<exe SHA-256 소문자>\n"` 을 SHA-256 으로 서명(IEEE P1363, 64바이트) → base64 → 릴리스 자산 `ClaudeUsageTray.exe.sig`. 버전을 묶어 예전에 서명된 exe 를 더 높은 태그로 다시 올리는 되돌리기를 막는다.
- 앱(`UpdateService.SelectUpdate`): exe 와 `.sig` 가 모두 있는 가장 새 릴리스만 업데이트로 본다. 받은 뒤 서명이 맞지 않으면 파일을 지우고 설치하지 않는다. 검증 없이 설치하는 경로는 없앴다(사용자가 직접 누른 경우도).
- 배포: 태그 push → CI 가 릴리스 생성 → 배포 PC 에서 `pwsh tools/sign-release.ps1 v<버전>`. 스크립트는 자산을 CI 가 올렸는지, 태그 커밋이 `origin/master` 에 있는지, 해시가 SHA256.txt 와 같은지, 키가 그 태그의 앱에 내장된 공개키와 짝인지 확인한 뒤에만 서명한다.
- `SHA256.txt` 는 계속 올린다 — v1.67.2 이하 앱은 그것으로 v1.67.3 을 받는다(서명을 보는 첫 버전까지는 옛 방식).

**결과·주의.**
- 서명을 빠뜨리면 v1.67.3 이상 사용자는 그 버전을 받지 못한다(조용히 "최신"). 릴리스 확인에 `.sig` 자산 확인이 들어간다(`AGENTS.md`).
- 개인키를 잃으면 이후 버전을 자동 업데이트로 낼 수 없다 — 사용자가 새 키를 내장한 버전을 손으로 받아야 한다. 키를 바꿀 때는 새 공개키를 넣은 버전을 옛 키로 서명해 내보낸 뒤 바꾼다.
- 배포 PC 가 장악되면 키도 잃는다. 이 결정은 GitHub 쪽 탈취를 막는 것이고, 배포 PC 보안을 대신하지 않는다.
